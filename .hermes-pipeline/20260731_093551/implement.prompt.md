# Implementation Plan: Add "Home" Nav Item to HR Sidebar

## 1. Restated Goal & Acceptance Criteria

**Goal:** HR users currently land on `/hr` (HRDashboardPage) at sign-in but have no sidebar entry to navigate back once they move to `/hr/candidates`, `/hr/employees`, or `/hr/cases`. Add a "Home" (HR dashboard) navigation item to the sidebar so they can return to `/hr` at any time.

**Acceptance criteria:**
- A new sidebar item labeled "Home" (or "HR Home") linking to `/hr` appears for users with role `org:admin` or `org:hr`.
- It renders **above** the existing Candidates / Employees / Cases HR items (top of the HR group), matching the pattern where a section's landing page comes first.
- Active-state highlighting works correctly: the item is highlighted **only** when on exactly `/hr`, and NOT when on `/hr/candidates`, `/hr/employees`, or `/hr/cases`.
- Clicking it navigates to `/hr` and renders HRDashboardPage.
- Non-HR roles (caregiver, coordinator-only, candidate) do NOT see the item.
- Works in both the desktop (`lg:flex` fixed aside) and mobile drawer sidebars; on mobile, clicking closes the drawer (`onNavigate`).
- No regressions to lint / typecheck / unit / build / e2e.

## 2. Files to Create/Modify

**Modify (primary):**
- `src/app/shell/Sidebar.tsx` — add one `NavItem` to the `navItems` array.

**Modify/verify (tests):**
- `src/app/router.test.tsx` — verify existing `/hr` route coverage; add a Sidebar render assertion if a Sidebar test exists, otherwise add a focused test (see §4).
- Potentially create `src/app/shell/Sidebar.test.tsx` if none exists (search shows no existing sidebar test) — a lightweight unit test for role-based visibility + active state.

**No changes needed:**
- `src/app/router.tsx` — the `path="hr"` route already exists (lines 413–422) rendering `HRDashboardPage` under `TenantRoleRouteGuard allowedRoles={['org:admin', 'org:hr']}`. No new route required.
- `convex/*` — **no backend changes**. This is a pure client-side navigation addition; no tenant-data functions, no `authHelpers.ts`, no codegen needed.

## 3. Step-by-Step Implementation

**Step 1 — Choose an icon.** Import `Home` from `lucide-react` (add to the existing import block at lines 3–16). `Home` is not yet used and is semantically correct for a dashboard landing.

**Step 2 — Insert the nav item.** In `navItems` (Sidebar.tsx), insert a new entry immediately **before** the "Candidates" item (currently line 91), so the HR group reads Home → Candidates → Employees → Cases:

```tsx
{
  label: 'Home',
  path: '/hr',
  icon: <Home className="h-4 w-4" />,
  roles: ['org:admin', 'org:hr'],
},
```

**Step 3 — Verify active-state logic (critical).** The existing active logic (lines 234–236):
```tsx
const isActive =
  locationPath === item.path ||
  (item.path !== '/' && locationPath.startsWith(`${item.path}/`))
```
For `path: '/hr'`, `locationPath.startsWith('/hr/')` would incorrectly mark "Home" active on `/hr/candidates`. **This must be handled** so Home is highlighted only on exact `/hr`. Two acceptable approaches:

- **Preferred (localized, low-risk):** add an optional `exact?: boolean` field to the `NavItem` interface; set `exact: true` on the Home item; adjust the active check to skip the `startsWith` branch when `exact` is set:
  ```tsx
  const isActive = item.exact
    ? locationPath === item.path
    : locationPath === item.path ||
      (item.path !== '/' && locationPath.startsWith(`${item.path}/`))
  ```
  This avoids changing behavior for any other item and precisely fixes the `/hr` vs `/hr/*` collision.

- Alternative: use React Router's `NavLink` `end` prop for exact matching and drive styling off its `isActive` render-prop instead of manual `locationPath` comparison. This is a larger refactor of the existing manual logic — **not preferred** given the "conservative/minimal" house rule.

Go with the `exact` flag approach.

**Step 4 — Formatting.** Match house style: 2-space indent, single quotes, no semicolons, trailing commas as in the existing array.

**Step 5 — Regenerate nothing.** No Convex changes → skip `npx convex codegen`.

## 5. Risks, Security & Edge Cases

**Security (HIPAA / multi-tenancy / auth):**
- **Low risk — no new attack surface.** No Convex functions touched, no tenant data read/written. Authorization is unchanged and already enforced twice: client `RouteGuard` (`TenantRoleRouteGuard allowedRoles={['org:admin','org:hr']}` on the `/hr` route) and server-side guards in whatever queries HRDashboardPage already calls. The sidebar item is cosmetic navigation; even if a non-HR user forced the link, the route guard + server `requireTenantRole` would block access. **Sidebar visibility must not be treated as the auth boundary** — it isn't here; the real gate stays on the route + Convex side.
- No PHI is added to the sidebar label/icon.

**Edge cases:**
- **Active-state collision** `/hr` vs `/hr/*` — the core risk; addressed by the `exact` flag (§3 Step 3). Without it, "Home" would wrongly stay highlighted across all HR sub-pages.
- **Role source:** `role` defaults to `'org:caregiver'` while `api.members.me` is loading (Sidebar.tsx line 160). During load, Home won't show until the member query resolves — acceptable, matches all other role-gated items.
- **`org:hr` vs `org:admin`:** admins also get the item (they can access `/hr`). Consistent with existing Candidates/Employees/Cases entries.
- **Label ambiguity:** "Home" could be confused with the app root `/` (Dashboard). Since HR users don't see the `/` Dashboard item (roles `org:admin`/`org:coordinator` only — an admin who is also HR would see both). To avoid confusion for admin+HR users, consider labeling it **"HR Home"** or **"Overview"** instead of "Home". Recommend **"HR Home"**.
